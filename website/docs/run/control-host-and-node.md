:::caution[Planned]
Nothing on this page can be installed from a release today, and no `weft` CLI exists. This page
describes the plan and what the specification already fixes. It will become an install guide
once a release ships.
:::

Runs today: a walking skeleton under
[`product/cloud/`](https://github.com/beyond10x/weft/tree/main/product/cloud) builds two
binaries. `weft`, the control host, serves the generated HTTP surfaces of `weft-api` and
`weft-control` and the node channel over a local state file; it has no login yet, and built
without its test feature it answers every request as one without a caller. `weft-agent`, the
node agent, joins its node with a join token, reports what it observed and opens its session on
the node channel. Heartbeats, lease renewal and the work list are not built, so no instance runs.
The gate runs a test build of both in its tests.

## The plan

- weft's domains in Rust, generated by ESS from the specification in `ess/`.
- A **control host** binary that runs the server components `weft-api` (the user API) and
  `weft-control` (state, scheduler, identity issuer, secret delivery).
- A **node agent** on every worker machine, built on substrate: the `weft-node` component of the
  specification, built today as the `weft-agent` binary.
- ESS systems deployed as workloads and run by [Spindle](https://beyond10x.github.io/spindle/).

## What the specification fixes

These hold for any implementation, because the specification and its gate hold them today:

- **The node dials out.** A node agent opens one long-lived session to `weft-control` over mutual
  TLS. A worker opens no inbound port. The session is specified in
  [`protocols/node-channel.yaml`](https://github.com/beyond10x/weft/blob/main/protocols/node-channel.yaml).
- **Joining.** The operator provisions a node from a node pool, which issues a join token; the
  node agent presents it to join. The node is then `Ready` and takes instances
  ([nodes and clusters](../concepts/nodes-and-clusters.md)).
- **Observed, not told.** The node agent reports what it observed (heartbeats, instances, usage),
  never what it was told. Times the control plane decides on are stamped by the control plane.
- **Lost nodes.** When heartbeats stop, the session is lost, assignment leases end and the
  instances are scheduled elsewhere.
- **Access.** A cloud is created `SingleUser` (one implicit admin, a local socket, no login) or
  `Federated` (browser login through an external identity provider), and keeps that mode.

The setup steps a full cloud needs, in order, are written out as the setup of
[`sim/experiments/full-setup.yaml`](https://github.com/beyond10x/weft/blob/main/sim/experiments/full-setup.yaml):
create the cloud, declare zones, register runtimes, create node pools, provision and join nodes,
open their sessions, create the default cluster, then tenants, accounts and quotas. weft-sim runs that setup against the specification
today ([run weft-sim](../simulator/run.md#simulate)).

## Placements (planned)

The design names how weft itself is deployed:

| Placement | Shape |
|---|---|
| `local` | one process is control plane and worker; single-user access |
| `hosts` | a control host and a node agent per host; workloads in microVMs |
| `aws` | node pools on EC2 launch templates, volumes on EBS, buckets on S3 |
| `kubernetes` | a formation as a namespace, links as network policies |

None of these is implemented.
